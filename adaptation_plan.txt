Target: Sari-sari_smart/ (Kotlin + Jetpack Compose)

PURPOSE
--------------------------------------------------------------------------------
This plan focuses exclusively on adapting the FRONTEND (UI/UX) from the web
application prototype to the native Android mobile app. Backend, database,
and API integration are intentionally excluded from this plan and will be
addressed in a separate phase after the frontend is complete.

The web prototype (git/Sari-sari_smart/) is a feature-complete mobile-first
HTML/CSS/JS application with:
  - 16 HTML pages (multi-page app structure)
  - 1 stylesheet (style.css, ~2,500 lines)
  - 1 JavaScript file (app.js, ~4,800 lines)
  - localStorage for data persistence
  - EN + FIL localization with 200+ string pairs
  - 13 tutorial string sets
  - Phone-frame design (393x852px)
  - 5-tab bottom navigation (Home, Stocks, Sales, Utang, Help)

GUIDING PRINCIPLES
--------------------------------------------------------------------------------
1. Copy the visual design exactly — use the web prototype as a pixel reference
2. Preserve all terminology, layout, and UX patterns for sari-sari store owners
3. Implement language switching (EN/FIL) and text size scaling
4. Implement the tutorial system with all 13 tutorial types
5. Replicate the phone-frame design language (rounded corners, green theme, cards)
6. Prioritize the three business pillars: Stock Tracker, Daily Cash Summary, Utang Notebook
7. No Room database, no SQL, no API integration — use in-memory state + SharedPreferences
8. The HTML prototype's data model (state management, localStorage) should inform the
   Android app's in-memory state approach

STAGE 4 — STATE MANAGEMENT (No Database) [COMPLETE]
================================================================================

  The web prototype uses a centralized JavaScript state object persisted to
  localStorage. The Android app mirrors this approach without Room:

  State Approach (no database):
  ─────────────────────────────────────────────────────────────────────────
  Session state: MutableState/MutableStateFlow in AppViewModel
  Persistence: SharedPreferences + JSON serialization via PersistenceManager
               Uses built-in org.json (JSONObject/JSONArray) — no extra deps

  Implementation:
  ─────────────────────────────────────────────────────────────────────────
  PersistenceManager.kt:
    - saveProducts()/loadProducts() — JSON array of Product objects
    - saveDailyEntry()/loadDailyEntry() — JSON object for today's entry
    - saveSpecificSales()/loadSpecificSales() — JSON array of SpecificSale
    - saveDebts()/loadDebts() — JSON array of CustomerDebt objects
    - saveEndOfDayData()/loadEndOfDayData() — JSON object for EOD state
    - saveCounters()/loadCounters() — ID auto-increment counters

  AppViewModel integration:
    - initPersistence() called from NavGraph via LaunchedEffect(Unit)
    - Loads saved data on startup; seeds demo data only if no saved data
    - Auto-saves every state change via StateFlow.collect() coroutines
    - resetAllData() clears both in-memory state and SharedPreferences

  State Entities Implemented:
  ────────────────────────────
  [✓] products — List of product objects with name, cost, price, qty, unit
  [✓] stockStatuses — Computed from Product.quantity (plenty/low/out)
  [✓] dailyEntries — { date, stockExpenses, earnings, grossProfit, etc. }
  [✓] specificSales — { date, description, amount, quantity, customer, etc. }
  [✓] debts — { customerName, totalAmount, remainingBalance, transactions }
  [✓] usedCustomerNames — Computed from debts list for autocomplete
  [✓] endOfDayData — { date, cashInDrawer, steps, finished }

  Key difference from Room: All state is in-memory and serialized to
  SharedPreferences as JSON strings, avoiding Room dependency entirely.
