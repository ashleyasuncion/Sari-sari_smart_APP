SECTION A — DEVELOPER PANEL ACTIVATION METHOD
================================================================================

  The web prototype uses Shift+N (keyboard shortcut) to open the developer
  panel. Since Android has no physical keyboard in normal use, the activation
  method must be adapted.

  Several options were considered for adapting the activation:

  Option A: Long-press on Help tab (bottom nav, 5th icon)
    - Pros: Simple, follows Android conventions (long-press for hidden actions)
    - Cons: Less "secret" feeling, users might discover by accident

  Option B: Sequence tap H-S-S-D (Home -> Stocks -> Sales -> Debts)
    - Pros: Fun cheat-code feel, very hard to trigger accidentally,
             always accessible since bottom nav is on every screen
    - Cons: Slightly more complex state tracking code
    - INITIALLY SELECTED, then REPLACED

  Option C: Rapid 5-tap on Stocks badge
    - Pros: Ties into existing UI, clever
    - Cons: Badge may not be visible (no low stock items)

  Option D: Two-finger long-press on nav bar
    - Pros: Impossible to trigger by accident
    - Cons: Not discoverable, non-standard gesture

  --- CHOSEN METHOD: Double-tap Help (Final) ---

  After testing, the sequence tap (H-S-S-H) was found to be unreliable in
  practice. The final activation method is:

  **Double-tap the Help tab in the bottom nav bar (within 600ms)**

  How it works:
    1. User taps Help once — normal navigation to Help page
    2. User taps Help again within 600ms — Developer Panel opens
    3. Timing resets after each tap (no penalty for wrong tabs)
    4. Works from any page, including while already on the Help page

  Why double-tap wins:
    - Simplest possible implementation (~10 lines of code)
    - No state tracking, no animations, no timeouts
    - Works reliably on any device, any Android version
    - Naturally discoverable by developers who know the feature exists
    - Hard to trigger accidentally (two fast taps on the same tab)
    - No perceptible delay: navigation fires immediately on each tap

  Visual feedback:
    - None (silent activation — the panel just appears)
    - Navigation is immediate with no animation delay

  |                                                     |
  |  -- Test Data Generators --                         |
  |  [Generate Sale]   [Generate Debts]   [Bulk Add]    |
  |  [Seed Sample Data]                                 |
  |                                                     |
  |  -- Reset Actions --                                |
  |  [Reset Today]    [Clear Inventory]  [Clear Sel..]  |
  |  [Reset ALL Data] (red)                             |

  --- Sub-section B1: Data Viewers ---

  Action: View Raw State
  -------
  JS Source: function viewRawState() -- line 3713
  Behavior: Opens a modal showing JSON.stringify(state, null, 2) of the
            entire application state object in a formatted <pre> block.
            Includes a copy-to-clipboard button.
  Android implementation: Modal bottom sheet with scrollable monospace text
    showing JSON representation of all AppViewModel state. Copy button via
    ClipboardManager.
  Android Status: [✓] Implemented

  Action: Export All Data
  -------
  JS Source: function exportAllData() -- line 3724
  Behavior: Prompts for filename (default: sari-sari-smart-data.json),
            creates a downloadable Blob with all state JSON, triggers
            download via temporary <a> element.
  Data exported: settings, products, customers, debts, usedCustomerNames,
                 stockStatuses, dailyEntries, specificSales, sales, endOfDayData
  Android implementation: Use ActivityResultContracts.CreateDocument to let
    user choose save location. Build JSON string via org.json (same approach
    as PersistenceManager), aggregate all state entities, write to URI.
    Alternative: Use ShareCompat to share JSON via any app.
  Android Status: [✓] Implemented

  Action: Import Data
  -------
  JS Source: function showImportDialog(), function importData(data) -- lines 3741-3762
  Behavior: Creates a hidden <input type="file"> trigger, accepts .json files,
            reads with FileReader, parses JSON, calls importData() which
            overwrites all state properties, then saves to localStorage and
            refreshes all rendered views.
  Validation: try/catch around JSON.parse with fallback to sample data
  Android implementation: Use ActivityResultContracts.OpenDocument to let user
    pick a .json file. Read URI content via ContentResolver.openInputStream().
    Parse with org.json.JSONObject, validate structure, then load into each
    PersistenceManager method. Show confirmation dialog if data exists
    ("Importing will overwrite all existing data. Continue?").
  Android Status: [✓] Implemented

SECTION D — EOD PROGRESS PERSISTENCE
================================================================================

  The web prototype has dedicated EOD progress persistence that saves and
  restores End-of-Day step completion state across page navigations:

  Functions:
    saveEodProgress() -- line 3617
      Saves to localStorage key 'sss_eodProgress_YYYY-MM-DD':
        - step1Done (boolean -- cash step display state)
        - step2Done (boolean -- stock check step display state)
        - step3Done (boolean -- debt payments step display state)
        - step1Value (string -- cash amount entered)
        - summaryVisible (boolean -- whether summary overlay is shown)

    loadEodProgress() -- line 3633
      Loads and returns parsed progress object, or null if none exists.

    clearEodProgress() -- line 3648
      Removes today's EOD progress from localStorage.

  Purpose: Since the web prototype is multi-page (different HTML files),
           navigating between pages would lose EOD progress.

  Android Status: [ ] The Android app uses a single-page NavHost, so EOD
                      progress is never lost during navigation. However, the
                      EOD state (which steps are completed, cash-in-drawer
                      value) is NOT persisted to SharedPreferences, so killing
                      the app mid-EOD will lose all progress.

  Implementation note:
    The Android app's EndOfDayScreen uses remember { mutableStateOf() }
    for step completion state, which means EOD progress is lost on:
      - Process death (app killed by system)
    Save EOD progress via PersistenceManager when steps are toggled.

SECTION E — PER-PRODUCT LOW-STOCK THRESHOLD
================================================================================

  The web prototype supports per-product low-stock thresholds:

    function getStockStatus(product) -- line 3640
      var threshold = product.lowStockThreshold || 5;
      if (product.quantity <= threshold) return 'low';

  Each product can have its own lowStockThreshold property. If not set,
  defaults to 5.

  The Android app:
    Models.kt -- Product data class does NOT have a lowStockThreshold field.
    AppViewModel -- getStockStatus() uses a hardcoded threshold of 5:
      THRESHOLD_LOW = 5

  Android Status: [ ] Missing per-product lowStockThreshold field and UI to
                      set it. All products use the same global threshold of 5.

  Implementation:
    - Add lowStockThreshold: Int = 5 to Product data class in Models.kt
    - Add a field in AddStockScreen's form (could be a slider or number input)
    - Update getStockStatus() in AppViewModel to use product.lowStockThreshold
    - Update PersistenceManager to save/load the new field
